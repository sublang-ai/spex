# Drafter 提示词

主导者在同一轮次中向每个 Drafter 发送相同的第一个提示词。
尖括号中的文本由主导者填写。

## 目录

- [主导者填写什么](#主导者填写什么)
- [起草一个解读](#起草一个解读)
- [改正解读的形式](#改正解读的形式)

## 主导者填写什么

| 占位符 | 内容 |
| --- | --- |
| `<behavior-item>` | 行为条目的全文，从其标题开始 |
| `<assertion-item>` | 断言条目的全文，从其标题开始 |
| `<example-items>` | 每个示例条目的全文，从其标题开始 |
| `<cited-items>` | 这些条目引用的其他每个条目的全文，或 `none` |
| `<declaration>` | `binding.yaml` 的 `values` 和 `events`，连同其中的注释，不含该文件的其他内容 |
| `<format>` | [formats.md](formats.zh-CN.md) 的*类型和值*、*解读*和*表达式语言*三节，一字不差 |
| `<reading>` | 该 Drafter 的解读，与保存时一致 |
| `<cause>` | `spex verify` 在 `Cannot be checked` 之后打印的原因 |

不要给 Drafter 别的任何东西：不给代码，不给通向代码的路径，不给守卫文件，不给其他解读，也不透露你预期什么。

## 起草一个解读

先引用：

> 行为条目：<behavior-item>
> 断言：<assertion-item>
> 示例：<example-items>
> 它们引用的条目：<cited-items>
> 声明：<declaration>
> 格式：<format>

然后是指令：

```markdown
按所引用的格式，把上面引用的断言起草成一个解读，写成一份 YAML 文档。

只依据所引用的条目和声明来工作。
不要阅读项目的代码、测试、历史或 guards/ 下的任何文件，也不要去找其他解读。
必须满足什么，要取自条目的文字，而不是取自你对软件行为的预期。
条目没有说定某种情形时，选择你认为最忠实于其文字的做法并继续；不要提问。

解读要说明：
- 它必须记住的状态，不超过断言所需；
- 对每个事件，它何时合法，以及状态如何变化；
- 以规则的形式，断言何时适用，以及那时观察到的效果必须满足什么。

只有当条目说明了某个事件何时可以发生时，才给它一个合法条件。
只陈述这条断言：不要为其他行为添加规则，即使条目暗示了这样的规则。
只使用已声明的值、事件、参数和效果字段，并且只使用表达式语言的形式。

用一个围栏代码块回复这份 YAML 文档。
在它之后，用平实的话列出条目没有说定的每种情形以及你的选择。
```

主导者原样保存围栏中的文档，放在项目要求的文件头注释行之下，并把这份列表留给步骤 3。

## 改正解读的形式

发给其解读无法被 `spex verify` 读取的 Drafter。
宿主允许时延续同一个 Drafter；否则向一个全新的 Drafter 发送第一个提示词，并加上这两段引用。

> 你的解读：<reading>
> 原因：<cause>

```markdown
上面引用的解读无法读取，原因如所引用。
改正它的形式，使它说出你原本的意思，其他一概不改。
不要阅读项目的代码或其他解读。
用一个围栏代码块回复整份 YAML 文档。
```
