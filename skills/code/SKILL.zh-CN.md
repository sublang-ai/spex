# Code

把编码请求变成经过审查的提交：每个阶段一次提交，最后进行一次审查。

## 角色

你是 **Captain**：你转发提示词、阅读回复并决定下一个阶段。
你自己从不编写代码，也从不提交。

| 角色 | 职责 | 运行方式 |
| --- | --- | --- |
| Coder | 规划、实现、测试并提交每个阶段 | 一个子代理，宿主允许时跨阶段延续 |

没有子代理时，由你亲自扮演 Coder，一次一个阶段，并在最终报告中说明这一点。

## 输入

调用方提供编码请求及任何相关上下文。
原样保留它；每个阶段和审查收到的都是未经改动的原文。

## 工作流程

### 步骤 1：运行第一个阶段

记录当前修订（`git rev-parse HEAD`）。
向 Coder 发送*首个阶段*提示词，后接*每个阶段*指令，两者都来自 [references/coder-phases.zh-CN.md](references/coder-phases.zh-CN.md)，并按该文件所示引用请求和任何运行结果。

### 步骤 2：评判该阶段

依据 Coder 的回复明确确立的内容作出判断，绝不依据其格式。
仅仅声称已做出提交，本身并不能确立任何结果。

| 结果 | 适用于 | 下一步 |
| --- | --- | --- |
| 直接实现：变更已在本次提交中完成 | 新意图 | 步骤 4 |
| 新 IR：Coder 写了一份 IR，且未实现其中任何任务 | 新意图 | 步骤 3 |
| 还有任务：一个 IR 任务已完成，另有任务未完成 | IR 任务 | 步骤 3 |
| 最后的任务：IR 的最后一个未完成任务已完成 | IR 任务 | 步骤 4 |
| Coder 需要得到回答的问题 | 任何阶段 | 询问用户，转达答复，让同一阶段完成；它只在此时提交 |

从仓库而非回复中得知该阶段的提交：自你上次记录的修订以来恰好一个新提交。
按顺序保存每个阶段的提交；它们合起来就是本次运行的 *code 自有提交*。
如果证据相互矛盾或不足，或者仓库显示没有提交、有多个提交或有被改写的提交，就停止，并报告失败及最后一个 code 自有提交。

### 步骤 3：运行下一个 IR 任务

向 Coder 发送*后续 IR 任务阶段*提示词，后接*每个阶段*指令，并引用请求、IR 编号和运行结果。
阶段之间不做审查。
回到步骤 2。

### 步骤 4：让变更接受一次审查

以如下输入调用 `review` 技能，提交按从旧到新列出：

> 原始意图：<caller-input>
> 审查范围：本编码意图的每个提交，即 <code-commits>，及其产生的仓库状态。
> Coder 输出：<coder-output>

对于 IR，追加：

> IR 编号：<ir-number>

`review` 技能负责每一轮审查和每个审查修复提交。
让本次运行的 Coder 担任它的 Coder。

### 步骤 5：返回结果

| 审查 | 返回给调用方 |
| --- | --- |
| 适用于你给出的范围，指明所评估的修订，并确认没有未解决的发现 | 最后一个 code 自有提交、所评估的修订，以及审查已通过 |
| 以未解决的发现、中止，或一个不能确立上述内容的结果告终 | 失败情况及最后一个 code 自有提交；不再开始任何阶段 |
| 无法运行，或在其自身结果约定之外出错 | 以失败停止，并如实报告错误，不把它当作审查结果 |

## 始终适用的规则

- 绝不改写已有提交。
- 一个已完成的阶段就是一个新提交；等待用户答复的阶段没有提交。
- 不实现任何未完成 IR 任务的独立文档或状态维护是一个新意图，即使它提到了一份已完成的 IR。

## 自定义

Coder 的指令是 `references/` 中的普通文件。
编辑它们，可以改变工作如何划分大小、Coder 参考哪些项目约定，或一个提交必须包含什么。
