# Reviewer 提示词

Captain 每轮组装一个提示词：一段开场，引用的上下文，然后是每一轮指令。
尖括号中的文本由 Captain 填写。

## 开场：第一轮

```markdown
针对审查范围开始一次新的审查。
紧扣原始意图，遵循它的要求。
当范围指明了提交时，阅读每个提交信息以了解其上下文和理由；否则在有助于确立该上下文的地方使用仓库历史和提交信息。
```

紧扣原始意图，遵循它的要求。
阅读最新审查修复提交的提交信息，并查看下面 Coder 的反馈。

## 每一轮

每一轮中，引用的上下文还包含原始意图、审查范围及其上下文，以及任何相关的运行结果。
把这段指令追加到提示词末尾：

```markdown
理解全貌，并系统地思考底层设计。
继续找出问题或改进点（如有），不要重复。
在各轮之间保持发现编号一致。
只标记对正确性、行为或规格质量有实质影响的内容——不标记风格、同样合理的替代方案或理论上的威胁。
对于规格，标记过时、缺失、过度规定或规定不足的规格（如有）。
避免代码或测试中不必要的复杂性，但如果某个根本性的设计缺陷留到以后打补丁的代价高于现在修复，就要标记它。

如果某个问题代表一类缺陷，就在审查范围内找出每一个值得修复的实例，而不是每轮只提出一两个，那会拖长审查。
对于任何反驳，接受它或提出质疑。
对于本次审查中已附理由被拒绝两次的任何发现，视为已解决，不要再次提出。

对于自之前任何一次已报告的运行以来输入未变的测试或构建，不要重新运行。
不要编辑文件或提交；只报告发现。

如有需要，参考 specs/map.md 获取上下文；核实它仍然准确。
如有需要，参考 specs/meta.md 了解规格要求；核实受影响的规格遵循它。
```

发现编号只在一次审查之内用作引用。
