# 状态根目录锁：故障背景与方案建议

**状态：**修订后的待审查提案（2026-09-29）。项目负责人已为状态根目录租约选择方案 A，并将 Playbook 会话租约及仓库 claim 纳入同一次审查；实施时可以一并修改。其余设计细节仍待确定。本文档不代表行为变更或规范变更已经获批。

## 目的与范围

Spex 需要两种不同范围的单实例保护：

- 桌面外壳使用 Electron 的 `requestSingleInstanceLock()`：再次启动同一个桌面应用时，聚焦已有窗口（[app-shell-2](../specs/packages/app-shell.md#app-shell-2)、[实现](../apps/desktop/src/main.ts)）。
- 核心的状态根目录租约：对于 Spex 自有文件，同一时间只允许一个核心或主目录级存储操作，包括桌面核心、服务端核心以及会修改该目录的存储命令（[DR-036](../specs/decisions/036-file-state-store.md)、[core-service-61](../specs/packages/core-service.md#core-service-61)、[storage-14](../specs/packages/storage.md#storage-14)）。Playbook CLI 写入会话文件时使用独立的逐会话租约，可以与核心同时运行。Electron 的应用锁无法覆盖这些主目录级写入者。

本提案比较**状态根目录租约**的几种保护方式，同时审查 Playbook 逐会话租约及仓库 claim 中相关的主机名／PID 问题。三种协调机制纳入同一次审查；实施时可以一起修改，Playbook 自有的格式及 CLI 行为须与上游协调。
已接受的约束是每个状态根目录同时只能由一个核心服务；具体采用 `.lock/owner.json` 是当前实现选择。

## 故障与观察到的行为

2026-09-28，`npm start` 完成构建并启动桌面应用，但核心启动时报错：`/Users/kgm/.spex` 被 `Minion.local` 上的进程 `25313` 占用。
已有的 `.lock/owner.json` 记录了该 PID 和主机名，但进程 `25313` 已不存在。
当时 `hostname()` 返回 `Mac.lan`，而这台机器的本地主机名为 `Minion`。
用户通过将 `.lock/` 重命名为带时间戳的备份，再运行 `npm start`，使应用成功启动：

```bash
mv ~/.spex/.lock ~/.spex/.lock.stale-$(date +%Y%m%d%H%M%S)
npm start
```

这一步保留了旧的所有者记录，同时让原 `.lock/` 路径不再存在；这次成功重试属于人工恢复，并非程序自动回收残留锁。
`.lock.stale-*` 备份会被主目录的 Git 规则忽略；不再需要它排查问题时，可以删除。

2026-09-29，用户还观察到：

| 退出或重启方式 | 观察结果 | 现有代码中的原因 |
| --- | --- | --- |
| 关闭应用窗口 | `.lock/` 消失 | `window-all-closed` 调用 `app.quit()`；`before-quit` 等待 `shutdown()`，后者停止核心并释放存储租约（[桌面主进程](../apps/desktop/src/main.ts)、[核心停止流程](../packages/core/src/service.ts)、[存储关闭流程](../packages/core/src/store.ts)）。 |
| 在运行 `npm start` 的终端按 Ctrl+C | `.lock/` 可能残留 | 源码启动脚本向独立的 Electron 进程组发送 `SIGINT`。Electron 主进程没有将该信号转为 `app.quit()` 的处理器，因此进程可能在异步关闭流程完成前结束（[启动脚本](../scripts/desktop-runner.mjs)、[桌面主进程](../apps/desktop/src/main.ts)）。 |
| 带着残留的 `.lock/` 重启 | 有时仍能成功 | 如果记录的主机名等于当前 `hostname()`，且 PID 已不存在，核心会移走旧目录并重试获取锁；如果主机名不同，则在检查 PID 前直接拒绝（[存储租约](../packages/core/src/store.ts)）。另外，若桌面应用仍在运行，Electron 可能先接管第二次启动，使核心根本不会检查此锁。 |

源码能够解释这些现象，但最初那个进程究竟为何退出，目前无法确定。
现有租约只检查 PID 是否存在，不校验进程身份；如果 PID 被系统复用，已退出进程留下的目录也可能被误判为仍在占用。
如果所有者文件无法读取，启动会按保守策略拒绝，并需要人工处理。

## 现有机制及其局限

核心以原子方式发布 `.lock/` 目录，其中 `owner.json` 记录 PID、主机名、获取时间和令牌。
只有令牌仍与自身一致时，核心才会删除该锁。
启动时，它可以回收同主机且 PID 已死亡的锁；遇到不同主机名，则认为无法检查对方进程是否存活。
[存储 Git 命令](../packages/core/src/storage-git.ts)也会占用同一个 `.lock/` 路径，因此更换机制时必须一并处理。

这个目录可以协调同一文件系统上遵守规则的 Spex 写入者，但进程突然终止后，目录仍会存在。
主机名可能变化；PID 存在也不足以证明原持有者仍持有租约。
此外，如果两台机器各自持有经异步文件同步服务复制的目录，当前机制也无法保证两者互斥；[DR-036](../specs/decisions/036-file-state-store.md)已明确将多机器并发写入排除在范围外。
观察到的 `Mac.lan`／`Minion.local` 差异证明主机名发生了变化，但不能据此确定是哪项系统设置或网络事件导致的。

本机安装的 `@sublang/playbook` 15.0.0 会话存储（`reference/sdlc/code.playbook/bin/session-store.js`）同样会先比较租约所有者的主机名，再探测 PID。
它允许注入 `hostname` 和 `probeProcess`，但 Spex 目前都没有传入，而独立运行的 Playbook CLI 会自行创建存储实例。
只在 Spex 注入稳定身份，无法修复 CLI 写下的租约或旧的所有者文件；还需要上游协作和过渡方案。
其仓库协调器（`reference/sdlc/code.playbook/bin/repository-effects.js`）也使用主机名／PID 判断所有权。同一次审查还需覆盖仓库 claim 的身份、残留所有者处理，以及现有 claim 的兼容方案。

## 候选方案

无论选择哪一种方案，Electron 的单实例锁都继续处理桌面窗口行为；它不能保护服务端或存储命令。

| 候选方案 | 收益 | 代价与局限 |
| --- | --- | --- |
| **A. 加固现有目录租约：**用保存在同步主目录之外的机器身份替代主机名；只有核对 PID 和进程启动身份后，才回收本机所有者的锁。 | 无需新增锁依赖，即可处理本次故障和 PID 复用；可以保留当前对其他主机的拒绝规则。 | 突然退出后文件仍会残留，不过能够确认死亡的本机所有者可以被回收。进程启动身份的核对、旧所有者文件、机器身份丢失以及 Playbook／CLI 的协同，都需要明确方案。所有权无法读取或核实时仍须保守拒绝。 |
| **B. 带超时的心跳租约：**定期刷新租约，超过期限就将其回收。 | 无需原生接口；不依赖进程探测即可从已死亡的所有者恢复。 | 仍活着的所有者可能因休眠、暂停或负载过高错过期限，之后与接管者同时写入。单靠超时不能满足“只有一个写入者”的约束；它只能用作诊断线索，或配合另一套权威准入及隔离机制。 |
| **C. 操作系统建议性文件锁：**在本机写入者的整个生命周期内持有非阻塞独占锁。 | 所有者死亡后，操作系统释放本机锁；残留元数据不再阻止下一次本机启动。 | Node／Electron 没有内置 `flock`／`fcntl` 接口；进程内实现需要原生插件，打包辅助程序则要维护另一份二进制。还须覆盖全部写入入口、打包、ABI 重建、描述符继承及旧版本共存。单靠本机操作系统锁既不执行当前根目录的其他主机拒绝规则，也无法修复 Playbook 会话租约。 |

如果选 C，锁目标应放在**可能被同步的主目录之外**，位于稳定的本机文件系统中，按状态根目录的规范化路径区分，权限保持私有。持锁期间保持描述符打开；正常释放时不删除或替换锁目标。必须验证拉起的 agent 子进程不会继承并延长锁的存活。`flock(LOCK_EX | LOCK_NB)` 是 macOS／Linux 上的一个选择，但如何在 Node／Electron 中接入和打包，是选择 C 的前提（[Apple `flock(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html)、[Linux `flock(2)`](https://man7.org/linux/man-pages/man2/flock.2.html)）。

**已选定的状态根目录租约方向（2026-09-29）：**加固现有目录租约（A）。B 不足以作为唯一准入依据；C 仅保留为对比方案，不是计划采用的根目录机制。Playbook 会话租约及仓库 claim 纳入同一次方案审查，也可以在同一轮实施中修改；具体改法和兼容方案仍待决定。

桌面应用还可以单独处理 `SIGINT`／`SIGTERM`，请求 `app.quit()` 以便 `before-quit` 停止核心；源码启动脚本则设置有界等待和升级终止。无论最终选择哪一种租约方案，这都能改善关闭流程，但仍须保证强制终止后的安全（[桌面主进程](../apps/desktop/src/main.ts)、[启动脚本](../scripts/desktop-runner.mjs)、[Electron 应用 API](https://www.electronjs.org/docs/latest/api/app)）。按照此前“审查后再开发”的要求，此项属于**获批后可独立实施**的工作。

上述方案都无法让未经协调的异步文件同步安全地支持跨机器同时写入。真正的多机器并发访问需要权威的单一写入者，或能强制执行写入所有权的分布式协调机制。

## 更新规范或实现前需要审查的事项

- **其他主机的处理规则：**当前根目录实现会拒绝可见的其他主机所有者；DR-036 明确对*会话*租约保留这一规则，并将多机器并发写入排除在范围外。需明确已选方案 A 如何识别其他机器、如何处理仅含旧主机名的记录，并确认是否保留当前拒绝行为。如果改变 Playbook 的会话规则，必须修订 DR-036。确定后的根目录规则应在实施前写入规范。
- **本机的主要机制：**根目录租约已选择 A；机器身份、进程启动身份核对、旧格式兼容及失败处理仍需在修订规范或实施之前形成具体设计。
- **Playbook 协同：**已确定纳入同一次审查，实施时可以合并。仍需明确上游会话租约及仓库 claim 的身份、进程探测改动，并兼容独立 CLI 和现有所有者记录。只在 Spex 传入 `hostname` 会遗漏这些路径。
- **兼容与身份：**定义如何处理旧 `.lock/owner.json`、Playbook 所有者记录、旧版本程序以及丢失的机器身份，避免新旧写入者并存；无法核实的情况继续保守拒绝。规范化根目录身份，并处理符号链接和不同路径写法。
- **写入及关闭流程覆盖：**包括桌面、服务端、存储 Git 命令、迁移流程和会话写入者；定义桌面应用的正常信号关闭及有界升级终止，同时保留 [app-shell-26](../specs/packages/app-shell.md#app-shell-26) 要求的 Node ABI 恢复步骤。
- **诊断信息：**尽可能报告已证实的活动所有者；无法确认时清楚说明不确定性。不能仅凭元数据认定操作系统锁仍被持有。

## 审查通过后的建议验证

用真实的竞争进程做集成／系统验证：桌面与桌面、桌面与服务端、核心与存储 Git；正常关闭与 Ctrl+C；强制终止后立即重启；主机名变化；PID 复用；通过 Spex 和独立 Playbook CLI 接管会话；竞争的 Playbook 仓库操作及残留仓库 claim 的恢复；以及旧版本过渡。
选择 C 时，还应验证残留元数据但没有操作系统锁、操作系统锁繁忙但元数据缺失、同步主目录配合本机锁目标，以及 agent 子进程比核心活得更久的情况。选择 A 时，应验证机器身份缺失或改变，以及无法核实进程启动身份的情况。还须确认竞争失败的一方不会修改受保护状态，且源码启动脚本在中断后仍会恢复 Node ABI。

审查通过后，应先将被接受的决定写入 Spex 规范，再更新核心、外壳和存储相关约束及其集成验证；Playbook 自有的规范和实现须与上游协调。
修改规范后，按 [AGENTS.md](../AGENTS.md) 的要求运行 `spex lint`。
